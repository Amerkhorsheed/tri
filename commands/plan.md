description: Break a spec or feature request into TRI tasks with dependencies and phases
argument-hint: "<spec, feature description, or path to a doc>"

**Preflight first — tier 1 and 2 in the tri-method skill.** This command writes task identifiers, so run the checks before changing anything: a dirty worktree, a rebase in progress, or the default branch under `branch-pr` all stop the work, and a stale ref means the identifier you allocate may already be taken.

Load the tri-method skill first. Read the spec/description given in $ARGUMENTS (read the file if it is a path). Decompose into independently verifiable tasks — one bounded increment each, no bundling. For each: pick phase, priority, dependencies (only real technical prerequisites — do not add ceremonial edges; unnecessary dependency edges are what serialize parallel work). Use `--phase NN` for a numeric phase, or `--phase NN-label` when selecting an exact named phase. When an existing task tree has one suffixed directory such as `phase-12-mobile`, numeric phase creation reuses it; multiple matches fail instead of choosing silently. Create tasks with `node ~/.tri/scripts/tri.mjs new-task --title "..." --phase NN [--dep ID]...`, then fill Objective, In/Out of scope, binary Acceptance criteria, Required tests, and exact Expected files/directories. Exact scopes let the scheduler run independent chains concurrently. Generated tasks start with `## Specification status` `Unrevised`; only set it to `Specified` after this run actually wrote the Objective and Acceptance criteria — a task is a named topic until its spec is written. Where decomposition has real alternatives — phase boundaries, whether something is one task or three, which dependencies are genuine — put those to the user with AskUserQuestion before creating the files. Finish with `validate` and `graph`, and show the user the wave structure so they can see the parallelism available.
