Load the tri-method skill first and run its **tier 1, 2 and 3 preflight** before anything else — dirty worktree, mid-rebase, detached HEAD, default branch under `branch-pr`, a stale ref, and a remote branch that already claims this task each stop or redirect the work. Then run `node ${CLAUDE_PLUGIN_ROOT}/scripts/tri.mjs next`. Tasks generated by `new-task`/`plan` carry `Specification status: Unrevised` and are flagged as such in the ready list — run `/tri:clarify` on one before claiming it (`claim` warns without `--force`), and never feed an Unrevised task into a batch run without the explicit `--allow-unrevised` override. If $ARGUMENTS names a task, claim it respecting the configured workflow (tri.config.json "workflow"): in branch-pr mode first check remote branches for the task ID (an existing branch is a claim), create the task branch from the default branch, then `claim <ID> --by <name>` (default: git user.name), commit, and **push the claim branch immediately**; in trunk mode commit and **push the claim immediately** on the shared branch. Verify the pushed branch/ref matches the local commit; a push failure stops the workflow. Then read the task file completely plus its linked ADRs/context before implementing. After implementation and evidence gates, commit and push the task branch, then ask whether to open or merge a PR into configured development base — never merge silently. If no task named, present the ready list and ask which to start.
