## TRI Method

This project uses the TRI delivery method (task register + decision registers + evidence gates). Any agent working here — Claude Code, Codex, or other — follows this loop:

1. Run `node ~/.tri/scripts/tri.mjs next` to see ready tasks; pick one (or the one you were told to do).
2. Run `node ~/.tri/scripts/tri.mjs claim <ID> --by <name>` before starting. Claims are dynamic and pull-based: claim when you start, not in advance; claim more whenever you finish. Honor the configured workflow (tri.config.json "workflow"): trunk — commit and push the claim on the shared branch; branch-pr — check remote branches for the task ID first (an existing branch is a claim), create `<task-id-lowercase>-<slug>` from the default branch, push the claim commit immediately, verify its remote ref, one task per branch per PR, and read the frontier only from the default branch.
3. Preflight before changing anything. **Always:** stop on a dirty worktree, a rebase or merge in progress, or a detached HEAD; in branch-pr workflow create the work branch from the default branch before the first commit (`<task-id-lowercase>-<slug>` for a task, `run/<date>-<scope>` for a batch) and never commit work to the default branch. **Before allocating any shared identifier** — a D-/B- number, an ADR number, a task id — run `node ~/.tri/scripts/tri.mjs sync`; it fetches remote branches and reserves identifiers introduced outside the configured default branch. **Before claiming** — `git ls-remote --heads origin`: a branch named for the task id means it is already claimed.
4. Read the task file completely, plus every linked ADR and context document, before editing.
5. Implement exactly that one task. No unrelated refactoring.
6. Record consequential assumptions in `tri/ASSUMPTIONS.md`. Record decisions you are not authorized to make in `tri/DECISIONS.md` as blocking entries — never choose silently.
7. Architectural decisions (new dependency, new service, new boundary, changed contract) require an ADR in `tri/adr/` before implementation.
8. Fill the task's Evidence section with commands run and observed results. Strict profile: also write `tri/evidence/<ID>-<date>.md`.
9. Run `node ~/.tri/scripts/tri.mjs validate` — must pass.
10. Run `node ~/.tri/scripts/tri.mjs done <ID>`, commit, push, and verify the remote ref. Ask before opening or merging a PR; never merge silently.

New work discovered mid-task: create it with `node ~/.tri/scripts/tri.mjs new-task --title "..." --phase NN [--dep ID]`, don't fold it into the current task. Use `NN-label` for an exact named phase. When an existing tree has one suffixed directory such as `phase-12-mobile`, numeric phase creation reuses it; multiple matches fail rather than choosing silently. If the project sets `taskTemplate`, the new file uses the project's own template and every one of its fields must be filled before the task is claimed. If the project sets `companionFiles`, `new-task` names files it will not edit for you — task indexes and pinned inventory counts — and those must move in the same change or the project's own validator fails. `companions` can add maintenance strategies and argv-array hooks; `node ~/.tri/scripts/tri.mjs companions --check` checks them.

Batch mode: an agent may execute several tasks in one run. Loop step 1-10 per task without pausing between tasks; track progress through `node ~/.tri/scripts/tri.mjs run-state` (`--start` with scope/mode/queue, `--done`/`--blocked` per task, `--finish` at the end; bare `run-state` prints what remains so a killed session resumes); a task needing an owner decision gets a B- entry and Blocked status while the run continues with other runnable tasks; halt only on a red gate after a real fix attempt or when nothing runnable remains. `next --json` and `status --json` provide machine-readable state.

Stop and report instead of proceeding when: a dependency is not actually met, an owner decision is missing, the task would require weakening a validation gate, or scope exceeds the task.
